# カートと注文 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ログインしたお客さんがサービス全体で 1 つのカートに商品を入れ、注文を確定するとストアごとの注文ができて在庫が減り、オーナーが注文を「支払確認」「発送済み」と進められ、お客さんが注文履歴で状態と支払い方法の案内を確認できるようにする。

**Architecture:** 第 1・2 段階と同じく DB はサーバー側だけが触る。`services/cartService.ts` と `services/orderService.ts` が購入者の `sub`／オーナーの `sub` を鍵に権限を守る。注文確定は 1 トランザクションで商品行を ID 順に `FOR UPDATE` ロックし、全部成功か何も起きないかにする。状態変更は「今の状態」を条件に入れた `updateMany` で競合を検出する。

**Tech Stack:** Next.js 16 / React 19 / Auth.js v5 / Prisma 7 + PostgreSQL / Tailwind CSS 4 / `tsx --test` / Playwright

**Spec:** `docs/superpowers/specs/2026-10-27-orders-design.md`

## Global Constraints

- 購入はログイン必須。カートは購入者の `sub` ごとに DB に保存。数量 1〜10（`MAX_QUANTITY = 10`）、カート 30 種類まで（`MAX_CART_ITEMS = 30`）
- 注文確定は全部成功か何も起きないか。商品行は ID 順に `SELECT ... FOR UPDATE`。問題の種類は `unavailable`（商品かストアが非公開）・`insufficient_stock`・`own_store`
- 注文はストアごとに 1 件。商品名・単価・ストア名・支払い方法の案内は注文時点の値を記録
- 状態 `RECEIVED`（受付）→ `PAID`（支払確認）→ `SHIPPED`（発送済み）、`CANCELED`（キャンセル）。オーナーは RECEIVED/PAID → CANCELED も可、お客さんは RECEIVED → CANCELED のみ。キャンセルで在庫を戻す（`productId` が残る明細のみ）
- 状態変更は今の状態を条件にした `updateMany`。0 件なら `conflict`（「注文の状態が変わりました。画面を更新してください」）
- `Order.storeId`・`OrderItem.productId` は ON DELETE SET NULL、`CartItem.productId`・`OrderItem.orderId` は CASCADE。新テーブルは RLS 有効
- 対応中（RECEIVED/PAID）の注文があるストアは削除不可（「対応中の注文があるため削除できません」）
- 他人の注文・UUID でない ID は 404。注文番号 = `id` の先頭 8 文字を大文字。日時は日本時間 `yyyy/MM/dd HH:mm`
- 入力：郵便番号 7 桁（ハイフン任意、`123-4567` で保存）、47 都道府県、住所 1〜200 文字、電話番号は数字とハイフンで数字 10〜11 桁、支払い方法の案内 1,000 文字まで
- 文言は日本語。サービスはフォームの値で所有者を選ばない（必ずセッションの `sub` から）
- 単体テスト `lib/*.test.mts`・`tests/*.test.mts`（`npm test`）、結合テスト `tests/integration/*.test.mts`（`npm run test:integration`）

## Review Focus

- 同じお客さんが「注文を確定する」を 2 回同時に押す → 注文は 1 組だけ、2 回目は `empty_cart`（カートは 1 回目で空になる）→ Task 4 のテストに含める
- カートに入れた後で価格が変わる → 注文には確定時点の価格が記録される → Task 4 のテストに含める
- オーナーとお客さんが同時にキャンセル → 在庫は 1 回だけ戻り、片方は `conflict` → Task 4 のテストに含める
- フォームを改ざんして数量 `100`・`-1`・`abc` を送る → `invalid_quantity` でカートは変わらない／足し算でも 10 を超えない → Task 3 のテストに含める
- 他人の注文 ID・UUID でない ID・他人のカート行 ID → お客さんにもオーナーにも `null`／`not_found`、何も変わらない → Task 3・4 のテストに含める
